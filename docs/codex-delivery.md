# Codex 端的投递约束（实测记录）

> 适用范围：用本工具包往 **Codex（GPT 桌面端）** 投消息时的边界。结论都来自本机实测，随版本可能变化。
> 不含任何个人信息与私有路径；示例里的会话号都是 UUID 占位。

## 一、Codex 没有对外的 prompt 接口

桌面端不提供「往某个会话塞一条消息」的公开 API。本工具包走的是本地 CLI 桥：

- `codex exec resume <UUID>`：同步续跑一轮，等它跑完拿结果（慢，2–3 分钟，消耗订阅额度）。
- `codex queue --thread <UUID> --message ...`：把消息排进队列，不阻塞。

## 二、两种投递方式的真实语义

| 方式 | 行为 | 适用 |
|---|---|---|
| `exec resume` | 需要一个「没被别人占用」的会话；被桌面端打开时会报 `already has an active writer` | 目标空闲、要同步结果 |
| `queue` | 消息先进入排队，**当前回合正常结束**才被消费；回合被中断或卡死，队列会一直挂着 | 目标正开着、可以等 |

要点：
- **queue 只是排队，不是送达**。要区分「已排队」「已进会话」「已处理」三种状态；查不到凭证就写未知。
- 回合被用户中断后，队列项会冻结；要么等下一轮自然结束，要么先归档。
- 桌面端正开着的会话，`exec resume` 一定失败；不要反复重试。

## 三、哪些目标到不了

- **云端会话**（ChatGPT 网页端那种）：本机没有 rollout，投不进去。
- **已归档的线**：需要先 `unarchive`（动之前问人）。
- **受保护工作区**（例如你的私密资料目录）：默认不投。

## 四、目标选择

- **不要按「最近活动」猜**。多条可投时必须点名（别名或 UUID）。
- 同一任务选定后应记住，直到出现新窗口再重新确认。
- 消息头里带发起方的回程地址（哪条腿｜哪台机｜哪个会话），对方按地址回话，不靠猜。

## 五、机器闸

投递前先过闸：检查目标是否存在、是否归档、是否云端、是否受保护、是否被占用、回合状态、是否已有排队。命中硬拒或需要确认的情况，就停下来问人，而不是硬投。

## 六、已知限制

- Codex 的实验性 app-server 支持 `turn/steer` 等真插话能力，但要求以非管理员身份启动守护进程；在关闭 UAC 的机器上起不来。这是平台层的限制，不是本工具包的 bug。
- **守护进程还有一道「目录私密性」检查**（2026-11-24 实测）：关闭桌面端、备份 ACL、把 `~/.codex` 改成只允许当前用户，它仍报 `socket directory is not private to the current user`；把整个用户目录改单人也同样失败。判断它会检查上层家目录，普通家用 Windows 账号基本满足不了——要跑起来得为 Codex 单独开一个专用 Windows 账户。而且即使跑起来，守护与桌面端是两套写入者，能否接管桌面端已开着的会话仍未验证。
- **结论**：在普通账号环境下，`queue` 是唯一稳定路径；能送达、能回话、能核结果，但不能中途插话。回合被中断时队列会冻结，需要等下一轮或归档重开。
- 版本升级后，`queue` / `exec resume` 的参数与行为可能变；升级后建议先跑一次只读探针确认。
