# 跨窗传话的节流阀（减少来回烧额度）

> 多窗口协作最常见的浪费：两个 AI 为了对齐细节来回传话，每轮都带全量上下文和客套。下面两条是低成本的刹车。

## 一、轮次上限提醒

在发起方记录「本任务连续来回次数」。达到阈值（建议 6 轮）时，不要继续自动往返，而是：

1. 输出一句话摘要：现在分歧点是什么、双方各自立场、缺哪条证据；
2. 把选择权交给人：继续、换人、还是就此收口。

落地可以是一个很小的状态文件：

```json
{ "task": "选窗器-收口", "rounds": 5, "limit": 6, "last_sender": "momo" }
```

发送前读一次，`rounds >= limit` 就停下来问人。

## 二、精简信封模式

默认消息带完整的身份头、回程地址、正文摘要。当同一个任务已经来回超过 3 轮，改用精简模式：

- 只发**结论 + 证据路径**（谁、改了什么、证据在哪个文件/哪条命令的输出）；
- 不再复述背景，不再互相致谢；
- 长文留在共享文件里，消息里只给路径。

示例：

```
[精简] momo→gpt | task=选窗器-收口 | round=4/6
结论：闸已覆盖 send_codex，picker 未接。
证据：F:\hub\...\验收.md#L12
请回：picker 是否接闸（是/否），不用解释。
```

## 三、什么时候不要节流

- 首次交接（需要完整背景）；
- 涉及不可逆操作（必须写清全貌）；
- 对方明显误解了任务（先纠偏，再谈节省）。

依据：本机多窗口实测的额度消耗模式；轮次与阈值为自拟经验值，未做外部验证。
